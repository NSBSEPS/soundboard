# Soundboard

Piano service business platform: client records, service history, self-scheduling, and a buy/sell list — replacing Gazelle.

## Setup

1. Create a Supabase project.
2. In the SQL editor, run `supabase/schema.sql` (creates tables + RLS policies + the `book_slot` function).
3. In Supabase Auth settings, enable email sign-in (or whichever method you want clients using).
4. Copy `.env.example` to `.env.local` and fill in your Supabase URL/keys (Project Settings > API).
5. `npm install`
6. `npm run dev`
7. Deploy to Vercel, add the same env vars there, connect your Supabase project.

## How access control actually works here

The important thing about this architecture: **the database enforces who sees what, not the app code.**
Every table has row-level security policies (see `schema.sql`). A client's Supabase session can
only ever get back rows tied to their `client_user_id` — even if a future bug in a page or API
route forgot to filter by client, Postgres itself won't return someone else's data. Don't
route around this with the service role key except in the one place it's needed (see below).

The one exception is `book_slot()`, a `security definer` Postgres function: it's the only way a
client's booking action can touch the `availability_slots` table (owner-only otherwise), and it
re-checks ownership internally before doing anything. That pattern — narrow, audited security
definer functions, rather than reaching for the service role key — is the right way to handle any
future case where a client needs to trigger something slightly outside their own row.

## Getting your first client accounts set up

Since most of your ~800 clients already exist as paper/spreadsheet/Gazelle records rather than
app users, `clients.client_user_id` is nullable on purpose. Recommended order:

1. Bulk-import all clients into the `clients`/`pianos`/`service_records` tables first (owner-only,
   no auth needed for this since it's server-side/admin work) — this is your data consolidation
   phase from before.
2. Only invite clients to create logins in batches, starting with your ~150 active clients.
   When a client signs up, link their new `auth.users` id to their existing `clients` row
   (match on email is the simplest approach).
3. Everyone else stays as a "dormant" client record you can still search, tune, and message
   the old-fashioned way, and can invite to the portal whenever it's useful.

## Estimates → proposed work

`estimates` is where work actually originates now: create an estimate (for an existing client
*or* a lead who isn't a client yet — that's why `estimates` has both `client_id` and `lead_id`,
with a check constraint requiring at least one), add `estimate_line_items`, and once you mark
it `accepted`, create the corresponding `proposed_work` row(s) with `estimate_id` set so you can
always trace a piece of proposed work back to the estimate it came from. This scaffold doesn't
include the UI for that yet (see build order below) — the schema is ready for it.

## Public SEO landing page & lead capture

`/piano-tuning-near-me` is a public, unauthenticated page targeting searches like "piano tuning
near me" and "piano rebuilding [your area]." It includes:

- `lib/service-area.ts` — the list of towns within 100 miles of 97360, generated by straight-line
  distance. Swap in real drive-time distances (Google Distance Matrix API) if you want precision,
  but straight-line is a reasonable starting point for SEO copy.
- Structured data (`ProfessionalService` + `FAQPage` JSON-LD) so search engines can understand
  the service area and surface FAQ answers directly in results.
- A lead form posting to `/api/leads`, which inserts into the new `leads` table using the
  **anon key** — safe specifically because the `leads_public_insert` RLS policy only allows
  `INSERT`, never `SELECT`/`UPDATE`/`DELETE`, for non-owners. A submitter can't read back their

Before this goes live: fill in `BUSINESS_NAME` and `PHONE` in `page.tsx` (left as placeholders),
and write real body copy in your own voice — the FAQ answers and service descriptions here are
starting drafts, not final copy. Search engines reward genuinely useful, specific content over
generic template text, so the more this reflects how you actually talk about your work, the
better it'll perform.

To turn a lead into a client: once you've quoted and they've agreed, create a `clients` row
(or reuse the `converted_client_id` column on `leads` to link it), then build their piano/estimate
records as normal.

## Importing your existing clients

`scripts/import-clients.mjs` reads a CSV (see `scripts/clients-template.csv` for the expected
columns — one row per piano, so a client with two pianos gets two rows) and creates the
`clients`/`pianos` records. Export from Gazelle to CSV, reshape it to match the template's
columns (a spreadsheet formula or a quick pass in Excel/Sheets is usually enough), then:

```
node --env-file=.env.local scripts/import-clients.mjs your-file.csv --dry-run
```

Check the dry-run output, then re-run without `--dry-run` to actually write. It uses the
service role key and bypasses RLS on purpose — this is a trusted script you run yourself, not
something exposed to the web. Note it's not idempotent yet: running it twice against the same
file creates duplicate clients, so keep track of what you've already imported (or ask me to add
an `--update-existing` mode matched on email once you're re-running it regularly).

## The estimate builder

`/owner/estimates` is where proposed work actually comes from now:

1. **New estimate** (`/owner/estimates/new`) — attach it to an existing client + piano, or to a
   lead who hasn't converted yet.
2. **Add line items** on the detail page while it's a draft — each one is a separate priced item
   (e.g. "Tuning — $150", "Replace 3 damper felts — $60").
3. **Send** it — marks it `sent` (email delivery isn't wired up yet, see TODO in `actions.ts`).
4. **Accept** — this is the step that actually creates `proposed_work` rows, one per line item,
   each carrying `estimate_id` so you can always trace it back. Two things are required first:
   the estimate needs a `client_id` (not just a lead), and a `piano_id`. If it started from a
   lead, there's a **Convert lead to client** button right on the page that creates the client
   record from the lead's info and re-links the estimate automatically.
5. Once accepted, the work shows up in that client's portal immediately (same RLS-driven query
   you saw in `/portal`).

This is intentionally plain — no styling pass yet, and each line item is a flat description +
amount rather than a rate/quantity breakdown. Both are easy to extend once the flow itself feels
right to use day-to-day.

## Eleventh pass — finishing the per-piano-type pricing refactor, and a near-miss worth naming

You asked how long it had been since I'd tested everything, in the middle of a multi-turn thread
building out real pricing data. Good question to ask, and the honest answer mattered: **the
previous message's refactor was incomplete.** The schema and the Services page had moved to
per-piano-type pricing (`service_catalog_prices`), but three files — the estimate detail page's

**Fixed properly, not patched around:**
- The estimate page now fetches each catalog item's prices as a nested array

- The add-phase form looks up the price matching *that piano's actual type* — and if the piano's
  type isn't set on its record, it says so plainly and leaves the price blank rather than
  guessing. An earlier version of this fix defaulted silently to "grand" when a type was missing,
  which would have autofilled a wrong price without any indication it was a guess — caught and
  removed before it shipped.
- The catalog-sync logic (the "update the standard price" / "save as reusable" checkboxes) now
  upserts into `service_catalog_prices` keyed by `(catalog_id, piano_type)`, not a column that no
  longer exists.
- Swept the whole codebase for any other reference to the removed column — zero remaining.

**Also new this round: the bulk price adjustment tool**, since your real numbers are ~10 years
old and priced under market. `bulk_adjust_prices()` is a single SQL `UPDATE` (multiplying every

I caught it myself before shipping: at nearly 1,000 price rows, hundreds of sequential
round-trips risks a serverless timeout. One statement, regardless of row count, is the right way

**Full pass, run just now, not assumed:** SQL structurally verified (parens, dollar-quoting,

a real TypeScript compile across every touched file, RLS confirmed present on all 15 tables, and

in this zip, not what's in progress.

## Tenth pass — fixing the actual Gazelle pain point: prices that never stick

The complaint was specific and correct: picking a task from a catalog is only half the fix if the
price still has to be retyped every time. The catalog previously had no price field at all —
deliberately, since I didn't know your prices — but that meant it solved the "what do I call this
task" problem and left the "what do I charge for it" problem completely untouched.

**What changed:**
- `service_catalog.default_price` — your standard price, set once, autofilled from then on.
- Picking a catalog item on an estimate now fills in the price too, not just the description and
  visit/location defaults.
- If you change the autofilled price (or it was never set), a checkbox appears —
  checked by default — to make that the new standard going forward. Correcting a price on a real
  job is how the catalog stays current, not a separate maintenance chore.
- Typing something new from scratch (not picked from the catalog) shows a "save this as a
  reusable service" checkbox, checked by default, with a category picker. This is the part that
  actually kills the retyping cycle at the root: the first time you bill for a task, it becomes
  reusable in the same motion — no separate trip to a settings page required for it to stick.
- `/owner/services` — the Master Service List for bulk setup (pricing everything at once) and
  ongoing maintenance (add/deactivate services, fix a name) — the deliberate exception being that
  day-to-day price *corrections* happen right on the estimate where you're already working, not
  here.

One deliberate design choice worth naming: a price correction on one estimate updates the
*standard* price (affecting every future estimate), not just that one line item. That's the
whole point — "the same job, just on a different instrument" should mean the same price without
you having to remember to keep two places in sync. A genuine one-off (a discount, an unusually
hard job) is still just a matter of unchecking that box.

## Ninth pass — reminders shouldn't fire mid-rebuild, and confirming they don't silently stop

Two related asks, one real gap and one confirmation.

**The gap:** `pianos_due_for_service()` had no concept of "this piano has an active rebuild
happening right now" — a piano mid-teardown for a multi-week project would still show up as
"due for tuning" the moment its 6-month interval passed, which is nonsensical (you can't tune a
disassembled piano). Fixed by excluding any piano with unresolved work tied to a **multi-item**
estimate — deliberately narrower than "has any pending work at all," since a simple single-item
routine tuning reminder sitting unscheduled is exactly the ordinary case this engine exists for
and should keep nudging every cooldown cycle as before. Only a genuine multi-phase project
(more than one line item, still in motion) gets excluded. A related second gap in the cron route
itself: a single-item shop-only task sitting at `in_progress` (not caught by the multi-item check
above, since it's only one item) would still have gotten a duplicate estimate created for it —
fixed by excluding `in_progress` from the route's own "is this piano already in motion" check.

**Caught my own mistake while fixing this:** my first edit to `pianos_due_for_service()` left a
duplicate `$$;` closing delimiter from the old function body — which would have been a genuine
SQL syntax error, exactly the kind of thing the structural checklist exists to catch before it
reaches you. Found and fixed it in the same pass, before packaging.

**The confirmation:** whether reminders keep going until you say stop — they already did.
`clients.active` (defaults to `true`) is the only gate in the due-for-service query, and I traced
through the cron route again to confirm a declined or ignored reminder keeps retrying every
cooldown cycle rather than silently giving up — there was no hidden stopping condition to find.
Nothing needed fixing there; worth stating plainly rather than changing something that wasn't
broken.

## Eighth pass — multi-phase projects (rebuilds) and a real service catalog

**The core problem with the old model:** every estimate line item became one `proposed_work`
item that needed a single appointment slot. That's right for a tuning, wrong for a rebuild that
spans weeks — refinishing isn't a moment you book, it's shop time with a duration, and later
phases usually can't start until earlier ones finish.

**What's new:**
- Each line item now has three extra properties: whether it **requires a client visit** at all
  (unchecked for shop-only phases like refinishing — those never touch `book_slot()`, the owner
  starts and finishes them directly from `/owner/jobs`), an **estimated duration** in days
  (informational, not enforced), and whether it **depends on the previous phase** finishing first.
- A new work status, `in_progress`, for shop-only phases: `proposed → in_progress → completed`,
  parallel to the existing `proposed → scheduled → completed` path for actual appointments.
- `start_phase()` — the shop-only equivalent of `book_slot()`. Enforces the dependency check
  atomically: if a phase is flagged as waiting on the one before it, starting it fails unless
  that previous phase (by `sort_order` within the estimate) is already completed.
- **The nuance you specifically flagged, and I'm glad you caught it:** `complete_work()` now only
  resets a piano's `last_service_date` (and the reminder engine's clock) once *every* phase tied
  to the same estimate is finished — not on every intermediate phase. Finishing "restringing"
  three weeks into a rebuild no longer makes the piano look freshly serviced. Every phase still
  logs its own `service_records` entry regardless, so the history is complete either way.
- `/owner/jobs` now has three sections: scheduled visits (unchanged), shop work not started (with
  a "Start phase" button, and a warning shown if it depends on an incomplete prior phase), and
  shop work in progress.
- The client portal shows the right thing per status now instead of collapsing everything into
  "Confirmed" — a real gap I caught while building this: it previously showed a self-schedule
  button for `proposed` work regardless of whether that work even needed an appointment, which
  would have been nonsensical for a shop-only phase.

**The service catalog** (`service_catalog` table, and the dropdown in `/owner/estimates/[id]`'s
add-phase form): pulled from real PTG-standard terminology rather than invented — the grand
regulation sequence (let-off, drop, key dip, aftertouch, backcheck, repetition spring) matches
what's actually taught and tested for RPT certification, and the rebuild phase list, voicing
technique names (filing, needling, hardening), and common repair categories come from the same
kind of sourcing. No prices are seeded — those vary far too much by region and technician to
guess at responsibly; you fill in your own per estimate. Picking a catalog item autofills the
description and sensible defaults (visit-required, location, dependency), but every field stays
editable — nothing's locked in from the catalog. This is also the seed of the Master Service
List we talked about earlier; add, edit, or remove rows in `service_catalog` as your own practice
differs from the general standard.

**One schema note if you've already run part of the old file:** `work_status` gained a new enum
value (`in_progress`) by editing the original `create type` statement directly, since you hadn't
gotten past the `is_owner()` error yet. If you'd already successfully created that type in a live
database before this fix, you'd need `ALTER TYPE work_status ADD VALUE 'in_progress';` run as its
own statement instead (Postgres doesn't allow adding an enum value inside the same transaction
as its first use).

## Seventh pass — a real schema bug, and invoicing/payments via Square

**You caught a genuine bug, not a setup mistake on your end.** `is_owner()` was defined at line
261 of the schema, but three policies earlier in the file (leads, and two inside the estimates
section) already called it — running the script top-to-bottom hit those before the function
existed, which is exactly the "function is_owner() does not exist" error you saw. Root cause:
an earlier pass added `is_owner()` next to `handle_new_user()` in a spot that made sense
narratively (near the auth trigger) without checking it was still *positionally* before every
policy that depends on it. Fixed by moving `is_owner()`, `handle_new_user()`, the auth trigger,
and profiles' own RLS setup to immediately follow the `profiles` table — first thing after the
one table everything else depends on, not somewhere later that felt organizationally tidy. I
also added a standing check for this exact bug class (function-used-before-defined, and the same
thing for foreign keys referencing a table before it exists) to the checklist I run before
calling anything done, so this can't quietly recur elsewhere in the file.

**Invoicing, closing a gap the build itself surfaced:** tracing through how invoicing would
actually work, I found that nothing anywhere ever marked a job "completed" or updated a piano's
`last_service_date` after the initial import — meaning the reminder engine would have silently
gone stale forever. Fixed with `complete_work()`, a single atomic function (same pattern as
`book_slot`/`accept_estimate`) that updates the work status, the piano's service date, AND logs
a `service_records` entry together, so those three can't drift out of sync.

**The flow:** `/owner/jobs` lists scheduled work → mark it completed → `/owner/estimates/[id]`
shows a "Create invoice" button once every job tied to that estimate is done → `/owner/invoices`
lets you send it, which creates a Square Payment Link, emails the client (a proper transactional
email — no marketing-style unsubscribe link, since that doesn't belong on a bill) → Square's
webhook (`/api/webhooks/square`) marks it paid automatically once payment clears → the client
portal shows a working "Pay now" button the whole time, not just in the original email, since
the payment link's actual URL is stored, not just its ID (an early draft of this only saved the
ID, which would've left the portal with nothing to link to if a client came back after losing
the email).

**Setup:**
- `SQUARE_ACCESS_TOKEN`, `SQUARE_LOCATION_ID`, `SQUARE_WEBHOOK_SIGNATURE_KEY` from the Square
  Developer Dashboard — use sandbox credentials while testing (`SQUARE_ENVIRONMENT=sandbox`,
  the default), switch to production credentials deliberately before real money moves
- In Square's dashboard, add a webhook subscription for the `payment.updated` event, pointed at
  exactly `{your domain}/api/webhooks/square` — the signature check is sensitive to this URL
  matching exactly what's configured there, trailing slash and all

**Being upfront about what I can't verify without a live Square account:** I wrote this against
Square's documented API shapes (Payment Links, webhook signature scheme), but I don't have
network access or real credentials to test an actual payment end-to-end from here. Two things
worth specifically confirming once you have sandbox credentials: that the webhook event shape
for `payment.updated` matches what the code expects (`event.data.object.payment.status` /
`.order_id`), and that the signature verification passes with your exact configured webhook URL.
If either doesn't match, it's a quick fix once we can see Square's actual response — I'd rather
flag this now than claim certainty I don't have.

**Important scope note on "compiling everything from your laptop":** what's built now is
genuinely useful — one searchable place for anything you choose to upload with metadata you
provide. What it does NOT do yet, and what would be a real, separate project to build well:

- Automatically extracting EXIF data (date/location) from photos
- Transcribing voice memos into searchable text
- Parsing email exports (.eml/.mbox) or calendar files (.ics) into structured records
- Any kind of automatic "here's everything related to this client" compilation across file types

Each of those needs different tooling (an EXIF library, a transcription service like Whisper,

transcription is wrong, how photos get linked to the right client automatically vs. needing
manual review, whether processing runs on upload or in a batch. Rather than build a shallow,
untested version of all four in the same pass as everything else this round, I'd rather ask:
**which of these matters most to you first?** That's the one worth doing properly.

## Fifth pass — Pianos list, matching a real Gazelle pattern

You shared a Gazelle screenshot showing a flat, searchable Pianos table (independent of the
Clients view) with a "Next Tuning Due" column — a genuinely good pattern, so `/owner/pianos`
now mirrors it, with one improvement: sorted by next-due date rather than status, so the most
urgent piano is always at the top rather than something you'd need to re-sort for.

Also added `pianos.room_location` (Gazelle's "Living Room" / "Basement" column) — a real field we
didn't have. It's now in the CSV import template and script too.

One thing worth knowing: search covers the piano's own fields (make, model, serial) but not
client name — searching across a joined table isn't something PostgREST's simple filter syntax
supports directly; it'd need a Postgres function or view. Flagging as a known limitation rather
than guessing at a fix that might not hold up. Also worth noting since it came up while building
this: the search box interpolates your query into a raw filter string that has its own syntax
where commas/parens are structurally meaningful. Not exploitable here (owner-only, behind RLS),
but escaped anyway — the same shortcut on a public-facing search box would be a real
filter-injection risk, and it's better to build the correct habit here than remember to fix it
later somewhere it matters more.

## Third pass — deep testing (concurrency, real type-checking, dead links)

You asked for something closer to what a dedicated tester would do, so this pass actually ran
tools instead of just re-reading code: a real TypeScript compiler pass (with hand-written stand-in
types for the packages that can't be installed in this sandbox — no network access here), and a
systematic cross-reference of every internal link/redirect against what actually exists.

**Two real build-breaking bugs, confirmed by the compiler, not guessed:**
- Three files used `React.ReactNode` / `React.FormEvent` without importing React — a genuine
  "cannot find name" error under strict TypeScript. Fixed everywhere it appeared.
- `estimates/[id]/page.tsx` called `.reduce()`/`.map()` on data from a `.single()` query without
  type annotations — this one's subtle: without configuring Supabase's generated Database types
  (which this project doesn't do), a `.single()` result genuinely types as `any` in real
  supabase-js, and TypeScript's strict mode flags the resulting bare callback parameters. That
  actually would have failed `next build`. Fixed with explicit annotations.
- Being upfront about the process: my stand-in types for React/Next/Supabase also produced a
  handful of *false* positives (complaints about `React.ReactNode` as a namespace, and about
  passing a `key` prop to components) that don't reflect how the real `@types/react` and
  `next/link` actually behave — I traced through why in each case rather than either "fixing"
  code that wasn't broken or leaving you unsure which errors were real.

**A dangling route that would have 404'd on first use:** middleware redirects unauthenticated
visitors to `/login`, but that page was never built in any prior pass — an empty folder existed
and nothing else. Built it now (magic-link sign-in, matching the auth pattern used everywhere
else). Also swept every `Link`/`redirect()` target in the codebase against the actual route
tree — this was the only dangling one.

**Two real concurrency races, the kind that only show up under load, not in casual testing:**
- `book_slot()` locked the availability slot but never the work item being scheduled — two
  concurrent booking attempts for the *same* work item could both pass the status check before
  either committed, each claim a different slot, and both mark the item "scheduled." Fixed by
  locking (`FOR UPDATE`) the work item too, and while in there, folded the ownership check into
  the same query so a client can no longer distinguish "doesn't exist" from "exists but isn't
  yours" by the error message alone — a minor enumeration leak, closed for free by the same fix.
- Accepting an estimate did "insert the work rows, then update the status" as two separate calls
  — a double-click on Accept, or the reminder engine and an owner's manual click overlapping,
  could both pass the checks and both insert duplicate work rows. Rebuilt as a single atomic
  Postgres function (`accept_estimate`, alongside `book_slot`) so the whole thing either succeeds
  completely or rolls back completely — the same principle applied consistently now, not patched
  around at the JS layer.
- The reminder cooldown had the same shape of bug: read-then-check-then-write, so two overlapping
  cron runs could both see stale data and double-email someone. Replaced with a single atomic
  `UPDATE ... WHERE` claim, same pattern as the other two.

**A gap I should have caught the moment I added a spam-prevention honeypot:** it only lived in
the Next.js route. The RLS policy underneath still let anyone write to `leads` directly via
Supabase's public REST API using the anon key — same key already sitting in your client-side
JS — completely bypassing the honeypot. Removed the public insert policy entirely; `/api/leads`
now uses the service role key server-side, making it the *only* path to creating a lead, so the
validation there actually holds.

**A real-world email-delivery landmine:** `/api/unsubscribe` mutated state on a plain GET request.
Corporate email security gateways and some email clients routinely pre-fetch every link in an
incoming email — including unsubscribe links — to scan for malware. If GET immediately
unsubscribed someone, those scanners would silently opt clients out before the email was ever
opened, which would quietly sabotage the very outreach this system exists for. Changed to a
confirm-then-POST pattern — GET only shows a page with a button; the actual opt-out requires a
human clicking it.

**Smaller hardening, for consistency with the CRON_SECRET fix from the last pass:**
unsubscribe-token comparison now uses the same timing-safe comparison, and client/lead names
(user-submitted, unsanitized) are now HTML-escaped before landing in raw email HTML strings —
low practical impact today since a name only ever appears in that same person's own inbox, but
it's the same bug class as any other unescaped-input-into-HTML issue, and worth closing before
this code gets reused somewhere the blast radius is bigger.

**A genuine Supabase/Next.js integration nuance I want to flag honestly rather than paper over:**
Supabase's client defaults to the PKCE auth flow, which means a magic link hands you a `code`
that must be exchanged for a session *server-side* before a protected page's middleware check
will see it — landing directly on `/portal` skips that exchange and would likely bounce people
back to `/login`. I added `/app/auth/callback/route.ts` to do that exchange properly, and pointed
every generated magic link at it first. This matches Supabase's own documented pattern for
Next.js SSR. **What I can't fully verify without a live Supabase project and no network access
here:** whether `admin.generateLink()` (used by the reminder engine) produces a link in exactly
this `?code=` format, or an older hash-fragment style that a server route can't read at all
(browsers never send URL fragments to the server) — this has changed across Supabase versions
and depends on your project's auth settings. **Please test the actual magic-link flow end to end
once deployed** — sign up via `/login` first (simpler case), then check a reminder email. If
clicking either link doesn't land you signed in, check whether the URL after clicking contains
`?code=` or `#access_token=` and let me know which — the fix differs depending on which one your
project actually produces, and I'd rather tell you that now than pretend certainty I don't have.

## Security & efficiency audit (first pass)

Went back through everything with fresh eyes. Real issues found and fixed:

- **Critical: a client-side RLS policy bypassed the booking function entirely.**
  `proposed_work_self_schedule` let a client directly set `status = 'scheduled'` with any
  `scheduled_at` value via a plain update — never touching `availability_slots`, meaning two
  clients could "claim" the same nominal time and the system would show both as confirmed.
  Removed. `book_slot()` (security definer) is now the only path to scheduling, exactly as it
  was designed to be from the start — this policy shouldn't have existed alongside it.
- **Missing signup trigger.** There was no mechanism that ever created a `profiles` row for a
  new user, meaning `is_owner()` would silently return false forever and nobody could ever be
  recognized as the owner. Added a trigger that auto-creates a `profiles` row (always as
  `'client'`, never self-assignable as `'owner'`) on signup.
- **No unique constraint on `clients.client_user_id`.** Two client rows could reference the same
  auth user, which would make `.single()` queries in the portal throw on ambiguous results
  instead of degrading gracefully. Added `unique`.
- **A real bug in lead conversion.** `convertLeadToClient` was writing a lead's zip code into the
  client's `address` field. Added a proper `zip` column to `clients` and fixed the mapping.
- **N+1 query in the reminder engine.** The "does this piano already have an estimate in
  progress" check ran once per due piano. Batched into a single query plus an index on
  `estimates(piano_id, status)` — matters once dozens of clients come due the same week.
- **A subtle auth bug in the cron route.** The `CRON_SECRET` check compared strings directly; if
  the env var were ever unset, `process.env.CRON_SECRET` becomes `undefined` and the check would
  actually match a request sending the literal header `Authorization: Bearer undefined`. Fixed to
  explicitly reject when the secret isn't configured, using a constant-time comparison.
- **No bot protection on the public lead form.** It's about to be linked from an SEO page, which
  reliably attracts scraper/bot spam. Added a honeypot field (hidden from real users, usually
  filled in by bots) that silently no-ops the submission.
- **`search_path` hardening.** Pinned `search_path = public` on `is_owner()` and
  `pianos_due_for_service()` for defense-in-depth, matching what `book_slot()` already did.

## The reminder engine — now fully automated

Per your call to skip the review step: this now sends real emails without you touching anything,
using [Resend](https://resend.com) and a one-click magic sign-in link so even a client who's
never logged in can land straight in their portal from the email.

**What happens daily** (`vercel.json` schedule):

1. `pianos_due_for_service()` flags anything past `last_service_date + service_interval_months`
   on an active client.
2. Skips any piano that already has a non-declined estimate in progress (checked in one batched
   query, not per-piano).
3. Creates an estimate with a "Routine tuning" line item at `DEFAULT_TUNING_RATE`, immediately
   marks it `sent`, and auto-accepts it — generating `proposed_work` right away so there's
   something real for the client to act on the moment they open the email.
4. Generates (or reuses) a Supabase magic sign-in link for that client's email — this is also
   what silently creates their auth account and links it to their `clients` row the first time,
   closing the earlier "no invite flow" gap.
5. Sends one of two emails depending on how overdue the piano is:
   - **Routine** (within the normal cycle): a straightforward "your piano is due" message.
   - **Dormant** (2+ years since last service — `DORMANT_THRESHOLD_DAYS`): stronger, more direct
     copy. I wrote this to be genuinely persuasive using real specifics (elapsed time, real risk
     to the instrument from years of neglect) rather than manufactured urgency or scare tactics —
     "most powerful" and "honest" aren't in tension here; specific true stakes outperform generic
     pressure anyway, and it protects your reputation with clients you're trying to win back.

**Compliance, since this is now unattended:** every email includes your business mailing address
and a working unsubscribe link (`/api/unsubscribe`, token-signed so only that client's own link
works) — required for automated commercial email under CAN-SPAM, not optional. Fill in
`BUSINESS_MAILING_ADDRESS` in your env vars before this goes live. `clients.email_opt_out`
tracks who's turned it off; the engine checks it before sending.

**Setup, in addition to what was already needed:**
- `RESEND_API_KEY`, `EMAIL_FROM`, `NEXT_PUBLIC_SITE_URL`, `BUSINESS_MAILING_ADDRESS`,
  `UNSUBSCRIBE_SECRET` (generate with `openssl rand -hex 32`), `REMINDER_INTERVAL_DAYS`
  (default 21) — all in `.env.example`
- Verify a sending domain in Resend before going live, or emails will land in spam regardless of
  how good the copy is
- Test the whole path locally first:
  `curl -H "Authorization: Bearer <CRON_SECRET>" http://localhost:3000/api/cron/reminders` — it'll
  actually send real email to whatever clients are due, so point it at test data before running
  against your real 800 clients

**On the automation trade-off:** this emails every eligible client automatically, no human in the
loop, throttled to at most once every `REMINDER_INTERVAL_DAYS` per client regardless of how many
pianos they have due. If a particular client relationship needs a different touch (someone
mid-dispute, a recent complaint, a piano you know is being sold), the right lever is
`clients.active = false` or `email_opt_out = true` to pull them out of automation before an email
goes somewhere awkward, rather than discovering it after the fact.
